# WidgetKit 固定自签名 PoC 验证

本 PoC 只使用假数据，独立于正式 Mihomo Meter。它分别验证“CI 打包与签名”和“用户安装后的共享容器运行时授权”；前者成功不能替代后者。

## 安装与复现

1. 从同一次 GitHub Actions artifact 取得 DMG、签名报告、诊断脚本和本说明。
2. 从 DMG 将 `WidgetSigningPoC.app` 复制到“应用程序”。打开应用，点击“重新写入测试快照”，记录主应用显示的写入与回读结果。
3. 添加“Mihomo Meter 签名 PoC”小组件，记录其读取结果与错误码。必要时移除后重新添加，以排除旧时间线。
4. 复现后尽快在“终端”执行 `bash widgetkit-signing-poc-diagnose.sh`。默认只检查最近 15 分钟；如操作较慢，可传入 1–60 的分钟数，例如 `bash widgetkit-signing-poc-diagnose.sh 30`。

诊断脚本只读已安装 PoC 的签名和系统注册信息，并筛选与本 PoC 有关的容器／沙盒日志。它只输出固定状态、计数和短证书指纹，不输出原始系统日志、完整文件路径、私钥或业务数据；不使用 `sudo`，不写文件，也不上传数据。若系统日志不可读取或时间窗内没有对应记录，会明确报告“证据尚不完整”，不能把它解释为授权成功。

## 证据判读

- `widgetkit-signing-poc-verification.txt` 是 CI 的**静态证据**：确认两个包使用同一固定证书、均声明目标 App Group，且嵌入与签名校验通过；它不能证明运行时容器可读。
- 报告与脚本展示的是 `codesign` 指定要求中的叶证书 SHA-1 短指纹；此前手工核验的 SHA-256 是同一证书的另一种摘要，两个字符串不能直接比较。
- 主应用写入和回读成功，而小组件出现主码 257，是两端**运行现象**；单靠它不能区分证书、系统注册和容器授权原因。
- 若诊断输出同时显示扩展注册路径匹配、同证书且无 Team ID、`containermanagerd` 对两端的群组请求均拒绝、TCC 拒绝 Widget，则能把 257 与该次运行时授权拒绝关联起来。主应用获准的 TCC 日志可进一步佐证，但日志未保留该记录时，应以主应用界面的实际写入和回读结果为准；没有拒绝日志时不得推断原因。

请勿把正式应用中的 Controller Secret、订阅地址、节点、真实流量或原始系统日志加入此 PoC 或反馈材料。正式 Release 签名与分发体系不受本 PoC 影响。
