# Swift 代码规范

## 1. 定位与适用范围

本文件是 Mihomo Meter 的 Swift 代码军规，适用于 `Sources/` 与 `Tests/` 中的 Swift 源码，以及相关代码审查。

本文件只约束代码表达、复杂度、文件预算、可测试性和 Swift 安全写法，不定义业务口径或模块职责：

- 模块分层、职责边界与代码落点以[架构概览](架构概览.md)为准。
- 敏感数据处理与日志边界以[数据与隐私](数据与隐私.md)为准。
- 构建、测试和提交要求以[贡献指南](../CONTRIBUTING.md)为准。

文档、代码与测试发生冲突时必须先停止并澄清，不得通过忽略规则或降低门禁继续推进。

## 2. 基础准则

1. API 命名遵循 [Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/)；调用处清晰优先于声明简短。
2. 保持原生 Swift、SwiftUI、AppKit 与系统框架优先；引入第三方依赖前必须先讨论收益、成本和替代方案。
3. 新实现先查找同仓同类类型、协议、测试和调用方式，以项目既有模式为锚点。
4. 优先完成当前明确需求，不为假设中的远期变化建立无调用方的抽象。
5. 编译警告必须处理；确实无法消除时，应在 Pull Request 中说明原因和影响。

## 3. 格式与命名

1. 所有 Swift 文件必须通过：

   ```bash
   xcrun swift format lint --recursive --strict Sources Tests
   ```

2. 使用 2 个空格缩进和 100 字符行宽；不得用手工对齐制造大段无意义空格。
3. 类型和协议使用 `UpperCamelCase`，属性、变量、函数和枚举成员使用 `lowerCamelCase`。
4. 名称表达业务或技术角色，不重复类型信息，不使用只有作者才能理解的缩写。
5. Bool 名称应能读成断言，优先使用 `is`、`has`、`can`、`should` 等前缀。
6. 有副作用的方法使用动词；无副作用的查询应读成名词短语或明确的查询动作。
7. 注释使用简体中文，解释约束、原因和非显然取舍，不逐行复述代码。

## 4. 文件、类型与访问控制

1. 一个文件原则上只承载一个主要顶层类型；紧密相关且很小的私有辅助类型可以同文件放置。
2. 文件名应与主要类型一致；协议实现可按 `类型名+能力` 命名并单独成文件。
3. `extension` 用于协议实现或清晰的能力分组，不得用来掩盖类型职责过多。
4. 访问级别默认取满足调用所需的最小范围，能用 `private` 时不使用更宽访问级别。
5. 默认直接依赖具体类型；只有存在稳定边界、多个实现或明确测试替身需求时才提取协议。
6. 新增职责出现独立变化原因、跨层依赖或重复逻辑时，应先判断是否需要拆分，再继续实现。

## 5. 函数与控制流

1. 一个函数只完成一个可清楚命名的意图；读取、转换、持久化和界面副作用不得无边界混合。
2. 优先使用 `guard` 处理失败和提前返回，避免持续增加嵌套层级。
3. 闭包或局部控制流连续嵌套超过两层时，应优先提取具名函数或领域操作。
4. 非默认参数超过 5 个时必须检查是否遗漏参数对象、稳定配置类型或职责拆分；不得只为缩短签名引入无语义容器。
5. 需要长期传递或表达业务含义的三个及以上返回值应建立具名类型，不使用大型元组。
6. 不吞掉错误，不用空 `catch` 伪装成功；错误转换应在明确的边界完成。
7. 生产代码不得使用无法说明不变量的强制解包、`try!` 或强制类型转换。测试中的固定常量可以使用，但失败原因必须直接可定位。

## 6. 并发与生命周期

1. UI 可观察状态和 AppKit、SwiftUI 交互应保持明确的 `@MainActor` 隔离。
2. 不使用 `Task.detached`、`nonisolated(unsafe)` 或未检查发送能力来绕过并发约束。
3. 长生命周期任务必须明确所有者、取消入口和失效条件，不得依赖对象释放碰运气结束任务。
4. 异步回调更新状态前应确认运行代次、会话身份或取消状态，避免过期结果覆盖当前状态。
5. 跨并发边界传递的数据应优先使用不可变值类型，并满足相应的 `Sendable` 约束。

## 7. 可测试性

1. 领域计算、状态转换和错误映射应可脱离界面与真实系统资源测试。
2. 只有在边界确实需要替身时才引入协议；不得为了测试覆盖率给每个类型机械增加协议。
3. 修复缺陷必须优先增加能复现问题的定向测试，再验证修复后的行为。
4. 测试名称描述场景和预期，不依赖执行顺序、真实 Keychain、真实 Controller 或本机用户状态。
5. 共享测试替身放入测试支持文件，不在多个测试类中复制近义实现。

## 8. 复杂度、文件预算与例外

预算用于发现风险，不替代职责判断。职责混杂、跨层耦合或多个独立变化原因出现时，即使未达到行数阈值也必须先评估拆分。

| 指标 | 软阈值 | 硬阈值 |
| --- | ---: | ---: |
| Swift 文件物理行数 | 300 | 450 |
| 单一类型体有效代码行数 | 220 | 320 |
| 单一函数体有效代码行数 | 60 | 120 |
| 圈复杂度 | 10 | 20 |
| 非默认参数数量 | 5 | 8 |

超过阈值后的处理规则：

1. 超过软阈值：继续修改前必须判断职责是否仍然单一，并在 Pull Request 中说明保留或拆分理由。
2. 超过硬阈值：不得继续叠加普通功能，应先拆分职责；安全修复或紧急缺陷只能做最小改动，且不得继续增加对应指标。
3. 既有代码超过软阈值时，不阻塞无关修改，但不得借无关任务顺手扩大；实质修改该区域时应至少停止增长。
4. 禁止通过无意义拆文件、大量空转发类型、跨文件 `extension` 或关闭检查来规避预算。
5. 生成代码和系统接口要求的固定结构可以例外，但必须保持最小范围，并在代码审查中说明原因。

当前 CI 已自动执行格式检查、构建和测试；复杂度与预算在接入稳定的机器检查前属于强制代码审查项，不得表述为已自动验证。

### 规则例外与演进

1. 规则例外必须有具体技术原因、最小影响范围和可验证结果，不接受“先关掉检查再说”。
2. 禁止对整个文件或目录长期关闭规则；局部关闭必须附简体中文原因。
3. 同一例外重复出现时，应优先修正规则、抽象或工具配置，而不是继续复制关闭指令。
4. 修改本规范时应同步检查 `CONTRIBUTING.md` 与 CI 命令；架构职责变化应维护架构文档，不得写入本规范代替。
